[SCENE 4 — TEACH · Point 1: Failures 1–3] (0:50–2:25)
SLIDE (max 12 words): Failures 1–3: Wrong Answer, Wrong Action, Wrong Source
DIAGRAM DESCRIPTION: Three-column layout. Each column has an icon, the

  Column 1 — "Hallucination" — brain icon with sparks — "Invents a

SCRIPT:
Failure number one — hallucination. The agent generates something that
sounds authoritative but is factually wrong. That warranty example?
Classic hallucination. The model had no source document to reference,
so it invented a policy. Three years instead of one. Coverage that
doesn't exist. Your users can't tell the difference between a real
answer and a confident fabrication. Forty-two percent of enterprise
agent incidents trace back to hallucination.

Failure number two — wrong tool call. The agent picks the wrong action.
Imagine a file management agent. A user says "clean up my old drafts."
The agent calls a permanent delete function instead of archive. The
data is gone. The reasoning in the logs looked solid — "user wants to
clean up, I'll remove the files." The action was catastrophic. The
reasoning was logical. The tool selection was wrong.

Failure number three — grounding failure. You gave the agent a retrieval
system. It retrieved the right documents. And then it ignored them. It
answered from its training data instead of the context you provided.
This one is subtle — your retrieval pipeline looks healthy, the right
documents are in the context window, but the generation step throws
them away. Seventy percent of RAG failures fall into this category.
The retrieval worked. The grounding didn't.

[SCENE 5 — TEACH · Point 2: Failures 4–6] (2:25–3:55)
SLIDE (max 12 words): Failures 4–6: Infinite Loops, Goal Drift, Boundary Violations
DIAGRAM DESCRIPTION: Three-column layout continuing the pattern.
  Column 4 — "Infinite Loop" — circular arrow icon — "Agent retries
  the same failing API call 47 times"
  Column 5 — "Goal Drift" — wandering path icon — "Starts on billing,
  ends debugging unrelated code"
  Column 6 — "Boundary Violation" — shield with crack — "Leaks PII,
  ignores role restrictions, executes unauthorized actions"
SCRIPT:
Failure number four — infinite loops. The agent hits an error, retries,
hits the same error, retries again. Forty-seven times. Your token bill
spikes. The user stares at a loading spinner. Nothing useful happens.
Multi-step agents are especially prone to this — one bad tool response
and the retry logic spirals. One team discovered their agent had burned
twelve thousand dollars in API costs overnight because a single tool
endpoint was returning a 500 error and the agent kept retrying.

Failure number five — goal drift. The agent starts on track. A user
asks about a billing charge. Three steps in, the agent is debugging
an unrelated API endpoint because one retrieval result mentioned it.
By step eight, it's summarizing documentation the user never asked
about. Each individual step looked reasonable in isolation. The
trajectory as a whole made no sense. Goal drift is invisible at the
step level. You only catch it by evaluating the full path.

Failure number six — boundary violations. The agent leaks personally
identifiable information in a response. It ignores its system prompt
restrictions. It calls a tool it was explicitly forbidden from using.
It reveals internal pricing logic to a customer. These failures don't
just break your product — they break trust, compliance, and sometimes
the law. One healthcare agent exposed patient diagnoses because the
guardrails were tested with polite prompts but never adversarial ones.

Step one — the agent retrieves the right knowledge base article. Green.
Step two — reasons about the billing question correctly. Still green.
Step three — here's where it breaks. It calls the order cancellation

Step four — the cancellation endpoint returns an error. The agent

Step five — after two failed retries, the agent gives up on tools

has no grounding. Failure mode one — hallucination.

Three failure modes in a single five-step run. And here's the critical
insight: a unit test on step one passes. A unit test on step two passes.
You'd only catch this by testing the full trajectory. That's why agent
testing is fundamentally different from traditional software testing.
