[SCENE 4 — TEACH · Point 1: The Deterministic Assumption] (0:55–2:10)
SLIDE (max 12 words): Traditional Tests Assume: Same Input → Same Output. Always.
DIAGRAM DESCRIPTION: Split-screen diagram. Left side labeled "DETERMINISTIC" — a function box with one arrow in, one arrow out, same every time. Examples beneath: calculator, database query, sort algorithm. Right side labeled "NON-DETERMINISTIC" — an LLM box with one arrow in, three arrows fanning out to different (all valid) outputs. Examples beneath: chatbot, support agent, summarizer.
SCRIPT:
Every test you've ever written rests on one assumption. Same input, same output. Call a function with 2 and 3. You get 5. Every time. Forever. That's determinism.

LLMs shatter that assumption. They sample tokens probabilistically. Even at temperature zero, minor API changes, model updates, or floating-point differences can shift the output. At temperature 0.7 — which is common in production — the variance explodes.

Here's the number that matters. A 2024 study ran GPT-4 on one thousand identical prompts at temperature 0.3. Only sixty-eight percent of responses were textually identical. The other thirty-two percent were semantically correct but worded differently. That thirty-two percent breaks every assertEqual in your codebase.

[SCENE 5 — TEACH · Point 2: The Evaluation Spectrum] (2:10–3:40)
SLIDE (max 12 words): The Evaluation Spectrum: From Exact Match to LLM-as-Judge
DIAGRAM DESCRIPTION: Horizontal spectrum bar, left to right, with four labeled stops:
  1. "Exact Match" (assertEqual) — icon: = sign — label: "Fragile, only for structured outputs"
  2. "Contains Check" (assertIn) — icon: magnifying glass — label: "Better, but misses paraphrasing"
  3. "Semantic Similarity" (embedding cosine) — icon: two overlapping circles — label: "Handles rephrasing, not reasoning"
  4. "LLM-as-Judge" (GPT evaluating GPT) — icon: gavel — label: "Evaluates meaning, most flexible"
Arrow beneath labeled "Increasing flexibility → Increasing cost"
SCRIPT:
Exact match is the strictest. assertEqual — the string must be character-for-character identical. Use it only for structured outputs like JSON keys or status codes. Never for natural language.

Contains check is one step better. Does the response include the word "Paris"? This handles some variation. But if the agent says "the French capital" instead, you miss it.

Semantic similarity uses embeddings. You convert both the expected and actual output into vectors, then compute cosine similarity. A score above 0.85 usually means same meaning. This handles paraphrasing well. But it struggles with reasoning — two answers can use similar words and reach opposite conclusions.

LLM-as-judge is the most powerful. You use a strong model — like GPT-4o — to evaluate whether the agent's response is correct, relevant, and complete. It understands nuance. The tradeoff? It costs tokens and adds latency. A single evaluation call runs about half a cent.

In this course, you'll use all four. The skill is knowing which one to reach for.

Right panel: a person at a desk answering a customer question with a speech bubble — label: "Correct, relevant, professional? Check all three." SCRIPT:
Think about it this way. A calculator gives you one answer. You check if it's right. Done.

But you don't test a human employee like that. If you ask a support rep "What's our refund policy?" — you don't demand the exact sentence from the handbook. You check three things. Is the answer correct? Is it relevant to the question? Is the tone professional? 

An LLM agent is closer to the employee than the calculator. It reasons. It paraphrases. It adapts to context. Your tests need to evaluate the same way a manager evaluates — on quality dimensions, not character matching.

Right file — `test_robust.py`:
```python
from deepeval.metrics import AnswerRelevancyMetric

def test_refund_policy():
    test_case = LLMTestCase(
        input="What's your refund policy?",
        actual_output=agent.ask("What's your refund policy?"),
    )
    metric = AnswerRelevancyMetric(threshold=0.7, model="gpt-4o-mini")
    assert_test(test_case, [metric])
    # ✅ Passes — response is relevant, score: 0.92
```
Highlight the threshold=0.7 line. Show terminal output: "Score: 0.92 | PASSED".
SCRIPT (voice-over):
Here's the shift in action. On the left — a fragile test. The agent said "thirty-day full refund" instead of "thirty-day money-back guarantee." Same meaning. Test fails.

On the right — a DeepEval evaluation. Instead of comparing strings, it measures answer relevancy on a zero-to-one scale. The threshold is 0.7. The agent scores 0.92. Test passes.

Notice what changed. The assertion moved from "does this string match?" to "is this response relevant enough?" That word — enough — is the paradigm shift. You're setting a quality bar, not demanding an exact string.

The threshold is yours to calibrate. A customer support bot might use 0.7. A medical information agent? You'd push that to 0.9. The business context drives the number.

SCRIPT:
One more shift. The traditional test pyramid says: many unit tests at the base, fewer integration tests in the middle, very few end-to-end tests at the top. For AI agents, the shape flips to a diamond. The thickest layer — where you invest the most — is component and trajectory evaluation. That's where agent failures actually live. Unit tests at the bottom are thin because prompt-level checks are fast but limited. System tests at the top are thin because they're expensive and slow. The diamond shape focuses your budget where it matters most.
