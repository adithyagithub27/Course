Component one — the LLM. This is the brain. It takes in the system
prompt, conversation history, retrieved context, and user query. It
outputs reasoning, tool call decisions, and final answers.

Think of the LLM as a brilliant but unreliable consultant. It can
analyze complex problems, connect dots across documents, and generate
articulate responses. But it sometimes makes things up. It occasionally
ignores instructions. And it gives slightly different advice every time
you ask the same question.

What can go wrong here? Three things. Hallucination — the brain invents
facts. Reasoning errors — the logic chain breaks somewhere in the
middle. Instruction drift — the brain slowly ignores the system prompt
over long conversations.

How would you test this? You'd check the output against ground truth.
You'd verify the reasoning chain is logically sound. You'd run long
conversations and check if the system prompt constraints still hold at
turn fifty. Module 3 teaches you exactly how to automate all three.

[SCENE 5 — TEACH · Point 2: Tools — The Agent's Hands] (2:00–3:15)
SLIDE (max 12 words): Component 2: Tools — The Agent's Hands in the Real World
DIAGRAM DESCRIPTION: The Tools component enlarged. A "tool belt" graphic

SCRIPT:
Component two — tools. These are the agent's hands. They let it reach
into the real world. Query a database. Call an API. Send an email.
Execute code. Without tools, an agent is just a chatbot with extra
steps.

Here's the critical testing insight: tools are the highest-risk
component. Why? Because they cause side effects. A bad text response is
embarrassing. A bad tool call can delete data, send money, or expose
private information.

Every tool has three failure surfaces. First — tool selection. Did the
agent pick the right tool? There are often multiple tools that sound
similar. Lookup order versus lookup customer. Cancel order versus return
order. The agent has to choose correctly every time.

Second — argument construction. Did the agent pass the right parameters?
The agent might call the right function but pass the customer's name
where the order ID should go.

Third — result interpretation. The tool returns data. Does the agent
read it correctly? A tool might return a status code of 404 and the
agent interprets it as a valid response.

Three failure surfaces per tool. Five tools on an agent? Fifteen things
to test. Just for tool use.

[SCENE 6 — TEACH · Point 3: Memory — The Agent's Notebook] (3:15–4:30)
SLIDE (max 12 words): Component 3: Memory — What the Agent Remembers and Forgets
DIAGRAM DESCRIPTION: Three-layer memory diagram.
  Layer 1 (top): "Short-Term Memory" — conversation window, labeled
  "Last N messages — typically 10–50 turns"
  Layer 2 (middle): "Working Memory" — scratchpad, labeled "What the
  agent has tried so far, intermediate results"
  Layer 3 (bottom): "Long-Term Memory" — vector database, labeled
  "Knowledge base, past interactions, retrieved documents"
Arrows show data flowing between layers. A red warning icon on the
boundary between short-term and long-term memory: "Information can be
lost in transfer."
SCRIPT:
Component three — memory. This is the agent's notebook. It has three
layers.

Short-term memory is the conversation window. The last ten, twenty,
maybe fifty messages. This is what the agent can "see" right now. When
the conversation gets too long, older messages fall off. The agent
forgets.

Working memory is the scratchpad. What has the agent tried so far? What
intermediate results has it collected? What's left to do? Some
frameworks make this explicit. Others rely on the conversation history
to serve double duty.

Long-term memory is the knowledge base — usually a vector database. This
is where RAG comes in. The agent retrieves relevant documents based on
the query and injects them into the context window.

What breaks here? Retrieval failure — the agent queries long-term memory
but gets back irrelevant documents. Ranked fourth when it should be
first. Context overflow — short-term memory fills up and pushes out
critical information from earlier in the conversation. A customer gives
their order number in message two. By message thirty, the agent has
forgotten it.

Testing memory means testing at different conversation lengths. Five
turns. Twenty turns. Fifty turns. Does the agent still remember the
critical facts? That's a test most teams never write.

[SCENE 7 — TEACH · Point 4: Planning — The Agent's Strategy] (4:30–5:30)
SLIDE (max 12 words): Component 4: Planning — How the Agent Decides What to Do
DIAGRAM DESCRIPTION: A planning flowchart showing the ReAct pattern.
  User Query: "Cancel my order and issue a refund."
  Plan Step 1: "Look up the order to confirm it exists"
  Plan Step 2: "Check if the order is eligible for cancellation"
  Plan Step 3: "Cancel the order"
  Plan Step 4: "Process the refund"
  Plan Step 5: "Confirm with the customer"
Each step has a "Reflect" checkpoint: "Did the previous step succeed?
Should I adjust the plan?"
A red branch shows what happens when Step 2 fails: "Order already
shipped — re-plan: offer return instead of cancellation."
SCRIPT:
Component four — planning. This is the agent's strategy engine. How does
it break a complex task into steps? How does it decide what to do first?

The dominant pattern is called ReAct — Reasoning plus Acting. The agent
thinks about the task, takes an action, observes the result, and then
reasons about what to do next. Each cycle refines the plan.

Watch a real example. User says: "Cancel my order and issue a refund."
The agent plans five steps — look up the order, check if it's
cancellable, cancel it, process the refund, confirm with the customer.

But what if step two reveals the order already shipped? A good agent
re-plans — "I can't cancel a shipped order. I'll offer a return
instead." A bad agent plows ahead and tries to cancel anyway, hitting
errors and looping.

Planning failures are the hardest to test. The agent's plan looks
different every time because it depends on intermediate results. You
can't hardcode the expected steps. You need to evaluate whether the
plan was reasonable given what the agent knew at each step. That's
trajectory-level evaluation — and you'll build it in Module 6.

circumstances change, or loop endlessly.

This is your testing map. Every agent test you write targets one of
these four components. Know the component, know the failure mode, design
the test.
