SCRIPT:
Why DeepEval over building your own evaluation harness? Three reasons.

First — it's pytest-native. You run evaluations with the `pytest` command. Your CI/CD pipeline already knows how to run pytest. Your team already knows how to read pytest output. Zero new infrastructure.

Second — fifty-plus built-in metrics. Answer relevancy, faithfulness, hallucination detection, toxicity, bias, coherence — all ready to use out of the box. You don't write the evaluation logic. You configure it.

Third — it uses LLM-as-judge under the hood. When you measure answer relevancy, DeepEval sends your test case to GPT-4o-mini, which scores the response and explains its reasoning. You get a number and a justification. That justification is gold for debugging — it tells you why a test failed, not just that it failed.

[SCENE 5 — TEACH · Point 2: The Four Core Concepts] (1:55–3:15)
SLIDE (max 12 words): Four Concepts: LLMTestCase, Metrics, assert_test, Datasets
DIAGRAM DESCRIPTION: Flow diagram showing four boxes connected left to right:
  Box 1: "LLMTestCase" — contains fields: input, actual_output, expected_output, context
  Box 2: "Metric" — contains: AnswerRelevancyMetric(threshold=0.7)
  Box 3: "assert_test" — takes test case + metrics, outputs pass/fail
  Box 4: "EvaluationDataset" — contains multiple LLMTestCases grouped together
Arrows flow: TestCase → fed into → Metric → evaluated by → assert_test. Dataset groups multiple TestCases.
SCRIPT:
Four concepts. That's all you need.

Concept one — LLMTestCase. This is the building block. It holds four fields. Input — the user's question. Actual output — what the agent actually said. Expected output — what the agent should have said. Context — the ground-truth information the agent had access to. Not every test case needs all four fields. At minimum, you need input and actual output.

Concept two — metrics. A metric is a scoring function. AnswerRelevancyMetric checks if the response addresses the input. FaithfulnessMetric checks if the response sticks to the provided context. Each metric has a threshold — a minimum score to pass. Set it based on your quality bar.

Concept three — assert_test. This is the glue. You pass it a test case and a list of metrics. It runs every metric against the test case. If all scores meet their thresholds, the test passes. If any metric falls short, the test fails. Just like a regular assert — but for AI quality.

Concept four — EvaluationDataset. A collection of test cases. Instead of writing one test function per case, you load a dataset and evaluate all cases at once. You'll use datasets heavily starting in the next lecture.

[SCENE 6 — SHOW / DEMO] (3:15–5:30)

File content:
```python
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric

def test_agent_response():
    test_case = LLMTestCase(
        input="What's your refund policy?",
        actual_output="We offer a 30-day guarantee. Full refund, no questions asked. Refunds process in 5-7 business days.",
    )
    metric = AnswerRelevancyMetric(threshold=0.7, model="gpt-4o-mini")
    assert_test(test_case, [metric])
```

Terminal command: `deepeval test run first_eval.py`

[SCENE 7 — TEACH · Point 3: The Built-In Metrics Library] (5:30–6:30)
SLIDE (max 12 words): 50+ Metrics — Pick the Right Ones for Your Agent
DIAGRAM DESCRIPTION: Grid of metric categories, each with 2–3 example metrics:
  "Quality" — AnswerRelevancyMetric, CoherenceMetric
  "Faithfulness" — FaithfulnessMetric, HallucinationMetric
  "Safety" — ToxicityMetric, BiasMetric
  "Agent" — ToolCorrectnessMetric, TaskCompletionMetric

Highlight "AnswerRelevancyMetric" and "GEval" as the two most commonly used.
SCRIPT:
DeepEval ships with over fifty metrics organized into categories.

Quality metrics — AnswerRelevancyMetric and CoherenceMetric. These check if the response makes sense and addresses the question.

Faithfulness metrics — FaithfulnessMetric and HallucinationMetric. These verify the agent sticks to its source data and doesn't fabricate information.

Safety metrics — ToxicityMetric and BiasMetric. These catch harmful or biased outputs.

Agent-specific metrics — ToolCorrectnessMetric and TaskCompletionMetric. These evaluate whether the agent used the right tools and completed the user's task.

And the most powerful one — GEval. This is a custom metric builder. You define the evaluation criteria in plain English, and DeepEval constructs a judge for it. "Did the response follow our company's brand voice?" "Did the agent include a disclaimer?" Whatever your business needs, GEval can measure it. You'll build custom GEval metrics in Module 4.

Two metrics handle eighty percent of use cases: AnswerRelevancyMetric for general quality, and GEval for anything domain-specific.
