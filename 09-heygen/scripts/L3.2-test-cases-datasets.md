[SCENE 4 — TEACH · Point 1: LLMTestCase Anatomy] (0:55–2:20)
SLIDE (max 12 words): LLMTestCase — The Building Block of Every Evaluation
DIAGRAM DESCRIPTION: Annotated diagram of an LLMTestCase object with five fields, each with a description and required/optional tag:
  - `input` (REQUIRED) — "The user's question or request"
  - `actual_output` (REQUIRED) — "What the agent actually responded"
  - `expected_output` (OPTIONAL) — "The ideal or reference response"
  - `context` (OPTIONAL) — "Ground-truth info the agent should use"
  - `retrieval_context` (OPTIONAL) — "What the RAG pipeline actually retrieved"
Color coding: green for required, blue for optional.
SCRIPT:
An LLMTestCase has five fields. Two are required. Three are optional but powerful.

Input — the user's question. "What's your refund policy?" This is always required. You can't test without a question.

Actual output — what the agent said. "We offer a thirty-day money-back guarantee." Also required. This is the response you're evaluating.

Expected output — the ideal answer. This is what a human expert would consider correct. It's optional — some metrics like answer relevancy don't need it. But correctness metrics do. Without an expected output, DeepEval can't judge accuracy.

Context — the ground-truth information. The actual refund policy from your knowledge base. This is what FaithfulnessMetric uses. It checks whether the agent's response matches this context — not whether it matches training data.

Retrieval context — what the RAG pipeline actually retrieved. This is different from context. Context is the truth. Retrieval context is what the agent actually saw. When these two diverge, your retrieval pipeline has a problem.

Here's the rule of thumb. For basic quality checks, input and actual output are enough. For correctness, add expected output. For faithfulness and hallucination detection, add context. For RAG evaluation, add both context and retrieval context.

A golden dataset is a curated collection of test cases that define what "correct" looks like for your agent. Think of it as the quality contract. Every test case in the dataset represents a scenario your agent must handle well.

The word "golden" matters. These aren't random examples. Each case is hand-crafted by someone who knows the domain. The expected outputs are reviewed. The context is verified against the actual knowledge base. Golden means trusted.

Your golden dataset is your quality contract. If you can't define what "correct" looks like for a scenario, you can't test for it. Build the dataset before you build the evaluation. It forces you to think about what the agent should actually do.

Python loader:
```python
import json
from deepeval.test_case import LLMTestCase

def load_golden_dataset(path: str) -> list[LLMTestCase]:
    with open(path) as f:
        data = json.load(f)
    return [
        LLMTestCase(
            input=item["input"],
            actual_output="",  # filled when agent runs
            expected_output=item["expected_output"],
            context=item.get("context", []),
        )
        for item in data
    ]

cases = load_golden_dataset("golden_support.json")
print(f"Loaded {len(cases)} test cases")
# Output: Loaded 10 test cases
```

[SCENE 7 — TEACH · Point 3: How Assertions Work] (5:50–6:50)
SLIDE (max 12 words): assert_test Runs Every Metric — All Must Pass
DIAGRAM DESCRIPTION: Flow diagram:
  LLMTestCase → feeds into → Metric 1 (Relevancy, score: 0.91 ✅) → AND gate
  LLMTestCase → feeds into → Metric 2 (Correctness, score: 0.83 ✅) → AND gate
  LLMTestCase → feeds into → Metric 3 (Faithfulness, score: 0.45 ❌) → AND gate
  AND gate → FAIL (because Metric 3 is below threshold)
Label: "One metric below threshold = entire test fails"
SCRIPT:
When you call assert_test, DeepEval runs every metric you provide against the test case. Each metric produces a score. If the score meets the threshold, that metric passes.

But here's the key — all metrics must pass for the test to pass. It's an AND gate. If relevancy scores 0.91 — pass. Correctness scores 0.83 — pass. But faithfulness scores 0.45 against a threshold of 0.7 — fail. The entire test fails.

This is by design. Remember the five dimensions from the last module. You don't get to trade off safety for correctness. A response that's correct but unfaithful to the source documents is still a problem. The AND gate enforces that every quality dimension you care about must clear its bar.

You control the thresholds per metric. Set relevancy at 0.7 and faithfulness at 0.8 if grounding matters more for your use case. The numbers are yours. The AND-gate logic is fixed.
