[SCENE 4 — TEACH · Point 1: The Chatbot Model] (0:55–2:05)
SLIDE (max 12 words): Chatbots: Text In, Text Out. One Step. Done.
DIAGRAM DESCRIPTION: Simple flow diagram. A user icon sends a message
arrow to a box labeled "LLM." The LLM box sends a response arrow back
to the user. One round trip. No loops, no branches, no external calls.
Below the diagram: three properties listed — "Stateless (or minimal
state)," "No tool access," "Single-turn reasoning."
SCRIPT:
A chatbot is the simplest thing you can build with an LLM. Text goes
in. Text comes out. One step. Done.

The user says "What's your return policy?" The LLM generates a response
from its training data. There's no planning. No tool calls. No memory
beyond the current conversation window. The model doesn't check a
database. It doesn't verify anything. It takes the prompt, predicts the
most likely completion, and returns it.

Testing a chatbot is straightforward. You send a prompt. You check the
response. The input-output relationship is direct. You can build a test
suite of a hundred prompt-response pairs and evaluate them. It's not
trivial — you still need semantic comparison because of non-determinism
— but the surface area is manageable. One input. One output. One thing
to check.

Now think about what happens when you give that LLM the ability to take
actions.

[SCENE 5 — TEACH · Point 2: The Agent Loop] (2:05–3:45)
SLIDE (max 12 words): Agents: Observe, Think, Act — Then Loop Again
DIAGRAM DESCRIPTION: Circular flow diagram showing the agent loop.
Starting at the top:
  1. "OBSERVE" — agent receives input or observes tool output
  2. "THINK" — agent reasons about what to do next (chain of thought)
  3. "ACT" — agent calls a tool, executes an action, or generates a
     response
  4. Arrow loops back to "OBSERVE" with the tool result
A "DONE" exit arrow branches off when the agent decides it has a
final answer. Multiple tool icons branch off from "ACT": database,
API, calculator, file system, email.
Around the loop, annotations show: "Step 1: Reason about user query,"
"Step 2: Call order_lookup tool," "Step 3: Receive tool result,"
"Step 4: Reason again — need more info?," "Step 5: Call tracking API,"
"Step 6: Generate final answer."
SCRIPT:
An agent runs in a loop. Observe — Think — Act. Then it observes the
result of its action and loops again.

The user asks: "Where's my order?" The agent doesn't just generate text.
It thinks: "I need the order ID. Let me check the user's account." It
acts — calls the account lookup tool. It observes the result — order
ORD-4821. It thinks again: "Now I need the shipping status." It acts —
calls the tracking API. It observes — shipped yesterday, FedEx, arriving
Thursday. It thinks one more time: "I have everything I need." It
generates the final answer.

Six steps. Three tool calls. Two reasoning cycles. Each step depends on
the result of the previous one. Each step can fail independently.

Here's the key insight for testing: you can't just check the final
answer. The answer might be correct even if the agent took a dangerous
path to get there. Or the answer might be wrong because step three
returned bad data. You need to test the entire trajectory — every
step, every decision, every tool call.

[SCENE 6 — TEACH · Point 3: Four Properties That Define an Agent] (3:45–4:50)
SLIDE (max 12 words): Four Properties: Reasoning, Tools, Memory, Goal Pursuit
DIAGRAM DESCRIPTION: Four-quadrant graphic. Each quadrant has an icon
and a label:
  Top-left: Brain icon — "Reasoning: Decides what to do and why"
  Top-right: Wrench icon — "Tool Use: Executes real-world actions"
  Bottom-left: Filing cabinet icon — "Memory: Remembers across turns"
  Bottom-right: Target icon — "Goal Pursuit: Works toward an objective"
Center label: "AGENT" connecting all four quadrants.
SCRIPT:
Four properties separate agents from chatbots. Every agent has some
combination of these.

Reasoning — the agent doesn't just pattern-match. It breaks problems
into steps, weighs options, and decides on a strategy. It has a chain
of thought, even if you can't always see it.

Tool use — the agent can take actions in the real world. Call an API.
Query a database. Send an email. Execute code. These are the agent's
hands. Every tool is a potential failure point.

Memory — the agent remembers. Short-term memory holds the current
conversation. Long-term memory might be a vector database with
knowledge articles. Working memory is the scratchpad where the agent
tracks what it's already tried.

Goal pursuit — the agent works toward an objective, not just the next
response. It can recognize when it's stuck, try a different approach,
and decide when the goal is achieved.

A chatbot has none of these. A basic RAG system might have one — tool
use for retrieval. A full agent has all four. And each one is a separate
axis you need to test.

Let's see this live. This is a support agent built with LangChain. Watch

User says: "I need a refund for order ORD-001." The agent thinks — "I
need to look up this order first." It calls the lookup tool with
ORD-001. Gets back the order details — shipped, a hundred forty-nine
ninety-nine, Wireless Headphones.

Now it thinks again — "Order found. I should process the refund." It
calls the refund tool. Gets a confirmation. Then it generates the final
answer: "I've initiated a refund of one hundred forty-nine ninety-nine
for your Wireless Headphones. You'll see it in five to seven business
days."

Five steps. Two tool calls. Two reasoning steps. One final answer. Every
piece is visible in the trace. And every piece can be evaluated
independently — did it call the right tool? Did it pass the right
arguments? Did it reason correctly? Did the final answer match the tool
output?

A chatbot test checks one thing. An agent test checks at least five.
That's the testing multiplier you're dealing with.
