### Script

[B-ROLL: A phone on a desk lights up at 11:40. The alert text reads: "AtlasTenantCostAnomaly: tenant ops hourly spend is 2.5x its daily average." Cut to a laptop opening.]

[AVATAR]
Eleven forty on a Monday morning. Your phone says one department's Atlas spend per hour is two and a half times its normal average. Nobody has complained. Nothing is down.

What do you open first?

Most engineers open the code. That's the wrong first move. In this section you're on call for three incidents, and before the first page I want to give you the habit that separates people who find root cause in ten minutes from people who find it in three hours. The order you ask questions in.

[SLIDE 1: The four questions, in order]
1. Timeline: when did it start, and what changed near that time?
2. Blast radius: who is affected, and who is not?
3. Hypothesis: write down two or three, with a prediction each
4. Evidence: which trace, metric or score would prove or kill each one?

Four questions. Always in this order.

Timeline. When did the symptom start, to the hour? What changed near that moment? A deploy, a config flag, a prompt label, a provider status post. Almost every incident has a change close to the first symptom. Find the change and you've found the neighbourhood of the cause.

Blast radius. One tenant or all four? One tool or every tool? And who is *not* affected? If three departments are fine and one is on fire, the cause lives in something only that department does.

[SLIDE 2: Hypotheses before evidence]
- Write two or three, never one
- Each with a prediction: "if traffic, requests per minute are up"
- Killing a hypothesis is progress
- Only then open the code

Hypotheses, plural, each with a prediction. "If it's a traffic spike, requests per minute will be up." "If it's a runaway loop, steps per request will be up." Writing the prediction first stops you from seeing what you want to see.

Then evidence. For each hypothesis, name the signal that would prove or kill it. Then go look.

[SLIDE 3: Which page answers which question]
| Question | Ops Console page | Signal |
|---|---|---|
| Is it traffic? | Traffic | requests per minute by tenant, with a shadow line |
| Is it bigger requests? | Cost | cost per session, input tokens per generation, by hour |
| Is it retries? | Reliability | failed LLM attempts per generation, by `error.type` |
| Is it one tool? | Reliability | error share per tool |
| Is it the provider? | Latency | `atlas.ttft_ms` p95, span p95 by type |
| Is it a change we made? | Retrieval, Quality | `atlas.retrieval.top_k`, `atlas.prompt_version` |
| Is it quality? | Quality | judge scores by hour and by prompt version |

Here's the map you'll use in every incident. Is it traffic? The Traffic page, requests by tenant against a shadow line. Is it bigger requests? The Cost page: if cost is up and traffic is flat, the money is going into bigger requests, not more of them. Retries and failing tools? The Reliability page. The provider? Time to first token on the Latency page is the provider's fingerprint. Something we changed? Every span carries the retrieval top-k and the prompt version, which is why you tagged them in Sections 4 and 5. And quality: judge scores by hour and by prompt version.

[SCREEN: Terminal in `03-code/`. Run `make incident N=1`. The text console prints: `requests=785 sessions=300 … total_cost=$2.3534`, the hourly cost bars spiking at 09:00 and 10:00, and the alert lines `[PAGE] latency_p95 p95 6819 ms > 4000 ms` and `[TICKET] cost_anomaly ops cost per request anomalous at 09:00, 10:00, 11:00`. Then `make console STORE=.atlas/incident-01.sqlite` opens the Streamlit console; click through the sidebar pages once.]

This is how you load an incident. One command, `make incident N=1`, imports the dataset into its own store and prints the text console: seven hundred and eighty-five requests, three hundred sessions, the hourly cost bars, and the alerts the console's batch rules found. Then `make console` with that store opens the same data in the browser, every page from the map in the sidebar. Everything runs offline. No API key, no cost.

[SLIDE 4: The incident template]
- Status line: what is broken, for whom, since when
- Timeline table: time, event, source
- Blast radius: affected / not affected
- Hypotheses: claim, prediction, status (open / confirmed / killed)
- Evidence: exhibit, where it lives, what it shows
- Root cause, fix now, prevention later

Open `10-resources/incident-template.md`. One page, and you'll fill one in for each incident. The block that matters most is hypotheses: the claim, the prediction, and a status of open, confirmed or killed. The evidence block is a list of exhibits, and each one says where it lives. "Cost page, tenant ops, nine to twelve" is an exhibit. "I looked at the dashboard" is not.

[SLIDE 5: How the incident labs work]
- Each incident: `brief.md`, `spans.jsonl`, `scores.jsonl`, `solution.md`
- Part A: the brief and six exhibits, then an eight-minute pause
- Part B: the evidence walked to root cause, fix and prevention
- Rule: do not open `solution.md` until Part B

Part A of each lecture gives you the brief and the exhibits without interpreting them. Then an eight-minute timer. Pause the video, fill in the template, and write your root cause in one sentence before you press play. Part B walks the evidence with you. One rule: don't open `solution.md` before Part B. You'll learn more from being wrong for eight minutes than from being right in ten seconds.

[AVATAR]
Three more things before your first page. Root cause is usually two things: a change that made the system fragile, plus a trigger that pushed on it. Fix now, prevent later: stop the bleeding first, even with a rollback. And write it down as you go, because forty minutes in you won't remember what you killed at minute five.

[SLIDE 6: Recap]
- Timeline, blast radius, hypotheses, evidence: in that order
- Use the page map to look first
- Write exhibits someone else can open

**Recap:** Investigate in order, timeline then blast radius then hypotheses then evidence, use the page map to look in the right place first, and write down what you know, think and have proven in the incident template.

**Transition:** Next, Incident 1: one department's spend has broken away from the others, and you have eight minutes to explain why.

### Speaker notes: common student mistakes / Q&A

- Mistake: opening code first. The Section 11 datasets are designed so the trace answers the question faster than the diff does. Say so explicitly.
- Mistake: a single hypothesis. Students who write one hypothesis tend to confirm it. Insist on two or three with predictions.
- `make incident` needs no Streamlit; the UI step does (`make install` installs it). If the console is slow on first load, it is reading the 300-session store; wait for the spinner.
- The B-roll alert text is the `AtlasTenantCostAnomaly` summary from `deploy/alerts.yml`; the 11:40 page time is from `incidents/incident-01-cost-spike/brief.md`.
- Instructor tip: pin a Q&A thread per incident titled "Incident N: your root cause in one sentence" and ask students to post before watching Part B.

### Script: Part B — the reveal

[AVATAR]
Time. Write your one sentence down if you haven't. Let's walk the evidence in the order from Lecture 11.1.

Timeline first. Two bends: nine and ten. Start with ten, because the provider told you. Exhibit four.

[SCREEN: Exhibit 4 again. tool error share flat at zero; `APITimeoutError` failed attempts 0.25 per generation at 10:00 and 0.16 at 11:00. Callout: all 72 failed attempts in the dataset carry `atlas.tenant = ops`.]

Tool errors: zero. Every tool, all day. If your first hypothesis was "a failing tool", the exhibit killed it, and that's fine. But failed LLM attempts, reason `APITimeoutError`, start at ten and stop by twelve. And every one of the seventy-two failed attempts in this dataset belongs to ops. That's the provider timing out on ops calls. Twenty-second timeout, two retries.

That's the trigger. But exhibit one bent an hour earlier. What happened at nine?

[SCREEN: Exhibit 5 again. `ops` mean top-k 4.0 at 08:00, 14.95 at 09:00; mean result tokens 1,288 at 08:00, 11,006 at 09:00. The other tenants stay at top-k 4 and about 1,300 tokens.]

At nine, ops retriever calls jump from top-k four to about fifteen, while everyone else stays at four. And what comes back goes from thirteen hundred tokens to eleven thousand. That's not more snippets. That's whole articles, untrimmed.

The eight fifty-five deploy. PR #412, "retrieval recall improvements". The knowledge base team had a real complaint: Atlas kept truncating the shipment policy, so answers missed the exceptions. Their fix, for ops only: top-k from four to twelve, the relevance floor `KB_MIN_SCORE` dropped to zero, and, because whole articles would otherwise be truncated, the context diet switched off. The model is allowed to ask for up to twenty, which is why the mean reads fifteen.

Blast radius answered too. One tenant, because the change was for one tenant.

[SCREEN: Exhibit 2 again. ops 115 requests 06:00 to 12:00 against 118 on the shadow line.]

And traffic? A hundred and fifteen ops requests between six and noon, against a hundred and eighteen on the shadow line. Killed. Same number of requests, each one far bigger.

Now the trace, because this is where the two causes meet.

[SCREEN: Traces page, session `s11-00110`. Turn 1: step 1 has two ERROR attempts of 20,000 ms each (`error.type = APITimeoutError`, 2,522 input tokens each, $0.0010 each) and one OK attempt (3,263 tokens); the retriever span shows `atlas.retrieval.top_k = 12`, `atlas.retrieval.hits = 10`, `atlas.tool.result_tokens = 8,218`; step 2 has two ERROR attempts at 10,785 tokens ($0.0043 each) and an OK attempt at 11,526 tokens. Turn 2 step 2: 19,294 tokens. Turn 3 step 2: 27,110 tokens. Each turn about 83 s.]

Turn one. The retriever returns ten whole articles, eight thousand two hundred tokens. Step two sends eleven and a half thousand input tokens. But look above it: two attempts that ran for exactly twenty seconds each, status error, `APITimeoutError`, each still carrying its input tokens and its cost. The prompt reached the model, so it was billed, even though we gave up on the answer. And the failed attempts get no cache discount.

Turn two, nineteen thousand three hundred tokens. Turn three, twenty-seven thousand. With the diet off, every turn drags the whole of the previous ones along. And every turn takes eighty-three seconds, which is the "over a minute" in the brief.

[SLIDE 3: One session, $0.103]
- Three turns, 268,815 input tokens billed
- Six successful calls: $0.033
- Twelve timed-out attempts: $0.070, 68% of the bill
- A normal ops session at 08:00: $0.0035

Add it up. Two hundred and sixty-nine thousand input tokens billed for three questions about leave. The six calls that answered cost three point three cents. The twelve attempts that timed out cost seven cents, sixty-eight percent of the session. Against a third of a cent for a normal ops session at eight.

[SLIDE 4: Hypotheses and verdicts]
| Hypothesis | Prediction | Exhibit | Verdict |
|---|---|---|---|
| Traffic spike | ops requests well above the shadow | 2 | Killed: 115 vs 118 |
| Failing tool, retry loop | tool error share up | 4 | Killed: zero tool errors |
| Provider timeouts | failed attempts from 10:00 | 4, 6 | Confirmed: the trigger, ops only |
| Bigger prompts | input tokens per generation up from 09:00 | 3, 5, 6 | Confirmed: the cause |

Traffic, killed. A failing tool, killed. Provider timeouts, confirmed, and they multiplied the bill. Bigger prompts, confirmed, and they made every retry expensive.

[SLIDE 5: Root cause, one sentence]
> PR #412, deployed at 08:55, switched the context diet off and raised retrieval top-k for ops, so from 09:00 ops prompts carried whole articles and untrimmed history; from 10:00 provider timeouts made Atlas send those prompts up to three times, billing input tokens on every failed attempt.

If your sentence had the timeouts, good. If it had the retrieval change, very good. If it had both and said which one multiplied the other, you're ready to be on call.

Now the fix, and what each part does on the full day.

[SCREEN: Ops Console, Compare replays page with four stores from `OFFLINE=1 make replay ... STORE=.atlas/<name>.sqlite`: baseline $56.28, p95 3,827 ms; `SCENARIO=cost_spike` $64.99, p95 6,763 ms; `SCENARIO=retry_storm` (the retrieval change rolled back) $58.00, p95 3,889 ms; `SCENARIO=retry_storm` with `ATLAS_MAX_RETRIES=1` $54.59, p95 3,934 ms, 392 errors.]

Fix now: roll the retrieval change back. `ATLAS_TOP_K=4`, `KB_MIN_SCORE=0.5`, context diet on. Replay the full four-thousand-session day to see what that buys. The incident day costs sixty-four ninety-nine. With the retrieval change rolled back and the same provider storm, fifty-eight dollars, against a fifty-six twenty-eight baseline. p95 drops from six point eight seconds to three point nine. The storm alone is a small problem. The bloat is what made it expensive.

Now the tempting second fix: fewer retries. With `ATLAS_MAX_RETRIES=1` the day costs fifty-four fifty-nine, a little cheaper than baseline. But the mock provider times out twice before it succeeds, so three hundred and ninety-two requests now end in an error. Cheaper and broken. A retry bound is a dial between cost and failure, not a fix.

[SLIDE 6: The fix this week]
- Now: `ATLAS_TOP_K=4`, `KB_MIN_SCORE=0.5`, `ATLAS_CONTEXT_DIET=1`
- No per-tenant path that switches the diet off
- Breaker: three consecutive failures; a success resets it
- Action: count failures over a window, not in a row

Why did no alert fire? `deploy/alerts.yml` has a rule called `AtlasJudgeScoreLow`. [SLIDE 5: Root cause, one sentence]
> The `production` label on `atlas-system` moved from version 1 to version 2 at 11:00 Monday without an offline eval; version 2 removed the citation and next-step rules, so grounded fell from 0.94 to 0.56 and resolved from 0.89 to 0.63, while cost and latency improved and the only quality alert could not fire.

Now the fix. One command.

[CODE: rollback with the repo's CLI]
```bash
python -m app.prompts promote --version 1
# calls telemetry.langfuse_setup.promote_prompt("atlas-system", 1, label="production")
#   -> Langfuse.update_prompt(name=, version=, new_labels=["production"])
# labels are unique across versions: this also removes "production" from version 2
```

`python -m app.prompts promote`, version one. It wraps `update_prompt` and moves the production label back. Labels are unique across versions, so version two loses it. Atlas picks it up within the sixty-second cache. No deploy, no restart. The property that caused the incident makes the rollback instant. Offline, the same rollback is `ATLAS_PROMPT_VERSION=v1`.

But rolling back isn't the prevention. The prevention is making sure a label can't move without evidence again.

[SLIDE 6: The gate]
- Promote the failing v2 traces to `atlas-failures` (`make dataset`)
- Promotion runs in CI: offline eval first, label second
- `promote` refuses below 0.85 grounded (your addition)
- Production label edits leave the UI; verify your plan's roles

Three moves. First, the failing version-two traces go into the `atlas-failures` dataset with `make dataset`, Lecture 8.6. They're now the regression suite for the next prompt change. Second, promotion happens in CI, never in the UI: run the offline eval against that dataset, and only then call `promote`. The threshold check, refuse below point eight five grounded, is yours to add in front of the CLI. Third, take production label edits out of the UI. Whether that's a role setting or a team rule, verify what your Langfuse plan supports.

- 8.6: v2 fails the `atlas-failures` dataset before it gets a label

Thirty seconds on prevention. Lecture 4.4 taught labels; a label change is a deploy. ### Speaker notes: common student mistakes / Q&A

- Most common miss: students find the prompt change but propose "edit v2 to fix it" instead of rolling back first. Fix now, improve later. Editing under pressure creates version three with its own surprises.
- "Was the product manager wrong to change the prompt?" No, and this is the blameless point for 11.5. The system let a behaviour change ship through a copy-editing interface. Fix the system.
- `promote` needs Langfuse keys; without them it prints "Langfuse is not configured … nothing changed". `make prompts` (`python -m app.prompts register`) pushes v1 and v2 and labels v1 `production`. `update_prompt(name=, version=, new_labels=)` is present in langfuse 4.16 (the locked version); re-verify before recording.
- Preset (`INCIDENT_PRESETS["quality_drift"]`): `prompt_regression` from 11:00 to 24:00, all tenants, `prompt_version=v2`. The mock keys off `V2_MARKER` ("avoid unnecessary references").
- `brief.md` says negative feedback "doubled in the afternoon" and cost is "down ~10%". The dataset shows noisy feedback (the drift report split at 11:00 shows user feedback +13%) and cost per request down 6.6%. Narrate the dataset; it makes the "feedback is too sparse" point stronger.
- `AtlasJudgeScoreLow` cannot fire because `atlas_judge_score` is never observed (the judge is a batch CLI). If a student wires `metrics.JUDGE_SCORE` into `evals/online_judge.py`, the rule works when the judge runs in the same process as the `/metrics` endpoint; that is a good capstone stretch.
- Restricting label edits by role: Langfuse RBAC and prompt protection vary by plan and version. Say "verify against current Langfuse docs" on screen.

### Script

[B-ROLL: Two postmortem documents side by side. Left: "Root cause: the KB team turned off the context diet without asking." Right: "Root cause: the context diet could be disabled per tenant through config, and no test or gate checked tokens per generation."]

[AVATAR]
Two postmortems for the same incident. The left one is true. The right one is useful. Only one of them prevents the next incident.

A postmortem has one job: it makes the same failure impossible, or at least loud, next time. In this lecture we write the Incident 1 postmortem together, live, and I'll show you the three ways these documents usually go wrong.

[SLIDE 1: The postmortem template]
1. Summary: three sentences, no jargon
2. Impact: numbers, with the source of each number
3. Timeline: time, event, source; detection and resolution marked
4. Root cause and contributing factors
5. Detection and response: how we found out, what slowed us down
6. Action items: type, owner, due date, verification

Open `10-resources/postmortem-template.md`. You filled most of it in during the investigation. The postmortem adds three things: impact in numbers, the detection gap, and action items with owners.

[SCREEN: VS Code, new file `incidents/incident-01-cost-spike/postmortem.md`. Type the summary.]

[CODE: summary block]
```markdown
# Postmortem: Incident 1, ops cost spike (Monday 2026-09-14)

## Summary
From 09:00 to 13:00 on Monday, Atlas requests for the ops tenant carried whole knowledge-base
articles and untrimmed history, after a retrieval change (PR #412) disabled the context diet
for ops. From 10:00 to 12:00 a provider timeout storm made Atlas send those large prompts up to
three times, and each failed attempt was billed. No other tenant was affected; no data was lost.
```

Summary. Three sentences a finance manager can read. What happened, why in one clause, who was affected and who wasn't. If the summary needs the word "span", rewrite it.

[CODE: impact block]
```markdown
## Impact
| Measure | Value | Source |
|---|---|---|
| Day cost (full-day replay) | $64.99 vs $56.28 baseline (+15.5%) | `make replay SCENARIO=cost_spike` vs baseline, Compare replays page |
| ops cost (full-day replay) | $28.98 vs $20.27 (+43%) | `make report`, Cost by tenant |
| Latency | ops p95 81.8 s in the incident sample; day p95 6.8 s vs 3.8 s | Latency page; `make incident N=1` |
| Most expensive session | `s11-00110`: $0.103, 68% of it on timed-out attempts | Traces page |
| Wasted provider calls | 72 timed-out attempts, all ops, 10:00-12:00 | Reliability page |
| Other tenants | none | Cost page, cost per hour by tenant |
```

Every number has a source column. That's not bureaucracy: the next person can reproduce the number, and you're not guessing. Notice the latency row. This was a cost incident, but users experienced it as eighty-second answers. Write down every kind of impact, not only the one that paged you.

[CODE: timeline block]
```markdown
## Timeline (UTC)
| Time | Event | Source |
|---|---|---|
| 08:55 | deploy PR #412: ops `top_k` 4 → 12, `KB_MIN_SCORE` 0, context diet off | deploy log; `atlas.retrieval.top_k` on retriever spans |
| 09:00 | ops input tokens per generation 4,018 → 12,032; cost per session ×6.5 | Cost page, unit costs, tenant ops |
| 09:15 | first anomalous 15-minute bin for ops (could have alerted) | Budgets page |
| 10:00 | provider timeouts begin on ops; 0.64 retries per request | Reliability page |
| 10:10 | (would have fired) `AtlasRetryStorm`, > 0.2 retries per request for 10 min | `deploy/alerts.yml`; not routed |
| 11:40 | `AtlasTenantCostAnomaly` pages on-call **(detection)** | alert history |
| 12:00 | provider timeouts end | Reliability page |
| 12:30 | root cause identified from `s11-00110` and the Retrieval page | investigation notes |
| 13:00 | retrieval settings rolled back; ops tokens normal **(resolution)** | deploy log; Cost page |
```

Time, event, source. Mark detection and resolution explicitly, because the gap between first symptom and detection is the number that matters most. First symptom nine o'clock, detection eleven forty: a hundred and sixty minutes. And look at the ten-ten row. I've written in the alert that *would* have fired. Writing the counterfactual into the timeline is how you justify the action item later.

[SLIDE 2: Root cause versus contributing factor]
- Root cause: removed, the incident does not happen
- Contributing factor: removed, it is smaller or found sooner
- Root cause here: the diet and top-k could be overridden per tenant with no gate
- Contributing: timeout storm, 20 s timeout, breaker blind to intermittent failures, retry-storm rule not routed

The root cause is the thing that, removed, means the incident doesn't happen: a retrieval change with no eval, no cost check and no gate. The provider storm is a trigger; the full-day replay shows it costs a dollar seventy on a normal day. The long timeout, the breaker that never sees three failures in a row, and an alert nobody routed are contributing factors. Each one removed makes the incident smaller or shorter, not impossible.

[CODE: detection and response block]
```markdown
## Detection and response
- Detected by: `AtlasTenantCostAnomaly` at 11:40, 160 minutes after the first symptom
- Could have been detected by: `AtlasRetryStorm` at ~10:10 (not routed); Budgets page anomaly at 09:15
- What helped: `atlas.retrieval.top_k` and `atlas.tool.result_tokens` on every retriever span
- What slowed us down: two causes with different start times; we chased the provider first
```

Detection and response. Four lines. How we found out, and how long it took. How we *could* have found out, with the time. What helped, which is usually an attribute somebody added months ago. And what slowed us down. Be honest in that last line. "We chased the provider first" is the most useful sentence in this document, because the next on-call will want to chase the provider first too. The gap between detected and could-have-detected is your best argument for every detection action item below.

[CODE: action items block]
```markdown
## Action items
| # | Action | Type | Owner | Due | Verified by |
|---|---|---|---|---|---|
| 1 | `test_context_diet_bounds_tokens` covers 3 turns × 12 articles | test | @agent-team | Wed | CI green; red when `ATLAS_CONTEXT_DIET=0` |
| 2 | remove the per-tenant override path for `context_diet`; cap `top_k` | instrumentation | @agent-team | Wed | `cost_spike` replay shows top-k ≤ 6 for ops |
| 3 | breaker counts failures over a 60 s window, not consecutive | test | @agent-team | Fri | fallback count > 0 in the `retry_storm` replay |
| 4 | route `AtlasRetryStorm` to the on-call rotation | budget | @platform | Fri | alert fires in a `make swarm SCENARIO=retry_storm` run |
| 5 | budget gate required on config PRs | test | @platform | now | `ATLAS_TOP_K=12 KB_MIN_SCORE=0 make budget-check` red |
| 6 | config changes that affect tokens or timeouts go through PR review | process | @eng-manager | now | config service requires a linked PR |
```

Action items. Every row has a type, and only four types are allowed: instrumentation, budget, test, or process. If it isn't one of those, it's a wish. "Be more careful with experiments" is a wish. "A test that fails when the diet is off" is an action.

Every row has an owner, a date, and a "verified by" column. Row five says the budget gate must go red on the settings that caused the incident. That's the strongest verification there is: the fix would have caught the past.

[SLIDE 3: Three anti-patterns]
- Blame: "the KB team turned it off." Fix the system
- Vagueness: "improve monitoring." Name the signal and where it pages
- Unverifiable: "add tests." Name the test and what makes it red

Three ways postmortems go wrong. Blame: "the knowledge base team turned off the diet." True, and useless. They had a real complaint and a lever that looked safe. Vagueness: "improve cost monitoring." Which signal, what threshold, where does it page? Row four names all three. Unverifiable: "add tests around the agent loop." If you can't say what would make the test red, you haven't designed a test.
